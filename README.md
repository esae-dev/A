# AEHA

![AEHA](public/brand/logo-light.svg)

기록과 스트릭에 집중하는 모바일 우선 습관 기록 PWA입니다. React, TypeScript, Vite, Dexie를 사용하며 서버·로그인·광고·알림 없이 브라우저 안에서 동작합니다. 외부 이미지나 웹폰트를 요청하지 않습니다.

## 화면과 동작

- **오늘의 루틴**: 루틴 생성·수정·삭제, 오늘 체크와 완료 취소. 미완료 → 완료 → 비대상 순으로 표시하며 체크 해제 시 저장된 수동 순서로 돌아갑니다. 왼쪽 핸들로 같은 상태 그룹 안에서 순서를 드래그해 변경할 수 있습니다. 이름, 메모, 색상, 매일 또는 선택 요일을 설정합니다. 오늘 대상이 아닌 루틴은 체크할 수 없습니다. 점 세 개 메뉴에서 수정·루틴 마무리·삭제를 선택할 수 있습니다. 마무리는 확인 후 홈과 오늘 진행률에서 제외하고 스트릭의 완료 기록에 보관합니다. 삭제는 확인 후에만 실행하며 기존 soft-delete로 기록을 보존합니다.
- **스트릭**: 내부의 진행 중/완료 기록 구분을 제공합니다. 진행 중에는 루틴별 현재·최장 연속 기록과 최근 26주의 날짜별 잔디를 표시합니다. 완료 기록에는 이름·색상·시작일·마무리일·총 완료 일수·최장 연속 기록과 마무리일에 고정된 26주 잔디를 표시합니다. 완료·미완료·비대상일·미래 날짜를 구분하며 좁은 화면에서는 가로로 스크롤합니다.
- **설정**: 언어 선택 목록(한국어/English), 라이트/다크 테마. 저장된 설정이 없는 사용자의 기본값은 한국어와 다크이며, 기존 라이트/다크 선택과 언어 설정은 그대로 유지합니다. 테마 버튼은 라이트/다크 순서를 유지하고 선택은 기기에 저장됩니다. 기존 시스템 테마는 처음 읽을 때 기기의 현재 라이트/다크 값으로 한 번 저장하고 이후 기기 테마 변경을 따르지 않습니다.

공통 버튼·선택 상태·내비게이션·앱 아이콘은 네이비를 사용합니다. 루틴별 표시·완료 체크·완료 잔디·현재 스트릭의 강조색은 사용자가 고른 색상을 사용합니다. 루틴 색상 수정은 기존 완료 잔디에도 즉시 반영되며 날짜별 기록은 그대로 보존됩니다. 지원 언어 목록은 `src/config.ts`에서 관리합니다.

처음에는 빈 목록으로 시작합니다. 예시 데이터나 사용을 막는 온보딩은 없습니다.

앱 이름·문서 제목·PWA 이름·아이콘은 AEHA로 통일합니다. 화면에는 제목과 필요한 상태·입력·오류 문구만 표시하며, 상단과 카드 간격을 간결하게 유지합니다. 비대상일은 옅은 회색과 패턴으로 표시하고 완료 색상보다 덜 강조합니다. 브랜드 변경과 관계없이 기존 IndexedDB 식별자·스키마와 PWA 설치 범위는 유지하여 저장 기록과 설치 경로를 보존합니다.

## UI 디자인

확정 로고와 앱 아이콘은 원본 자산을 그대로 사용합니다. UI는 따뜻한 아이보리(`#F6F5F3`)·화이트 카드와 딥 네이비(`#304565`), 다크 모드는 네이비 배경(`#121A27`)·차콜 카드(`#1B2534`)와 실버 블루(`#A7B8D3`)로 구성합니다. 루틴 고유 색상은 공통 UI 색상과 독립적으로 유지합니다. 공통 버튼은 네이비/실버블루를 사용하고, 루틴의 코랄 등은 해당 루틴 기록에만 적용합니다.

페이지 제목과 통계 숫자의 굵기, 카드·컨트롤의 반경과 여백을 절제했습니다. 설정은 일정한 폭의 왼쪽 라벨과 남은 폭을 채우는 오른쪽 컨트롤로 맞추며, 360px 이하에서는 같은 좌우 여백의 세로 스택을 사용합니다. 체크 버튼은 시각적으로 작게 보이면서 44px 터치 영역을 유지하며 추가 버튼은 48px입니다. 짧은 화면에서는 추가 버튼을 상단에 표시합니다. 내비게이션 높이와 safe-area를 반영한 하단 여백으로 마지막 콘텐츠까지 스크롤할 수 있습니다.

잔디는 26주 원본을 유지하면서 화면에 완전한 주 열이 들어가도록 너비를 맞춥니다. 그래프 안에서만 가로로 스크롤하고 월·요일 레이블과 셀 간격을 정렬합니다. 비대상일 패턴 대비는 낮추고 네 상태의 배경·패턴·테두리를 구분합니다. 이 조정은 표시 계층에만 적용되며 날짜·일정·스트릭 계산은 변경하지 않습니다.

메모가 있을 때만 제목·반복 일정 아래에 얇은 구분선과 약한 배경 대비의 보조 패널을 표시합니다. 줄바꿈을 유지하고 긴 단어도 줄바꿈하며, 체크·편집·드래그 핸들은 메모가 아닌 기본 정보 영역에 정렬합니다. 카테고리는 화면과 입력 폼에서 제거하지만 기존 필드는 보존합니다. 새 루틴에는 `other`를 저장하고 기존 루틴 수정은 원래 카테고리를 유지합니다.

반복 빈도와 요일 선택은 선택된 항목을 네이비/실버블루로 채우고 미선택 항목은 외곽선으로 구분합니다. 7개 요일을 균등하게 배치하고 최소 46px 높이를 유지합니다. 요일 변경은 기존처럼 내일부터 적용됩니다.

루틴의 6색 프리셋은 다음 순서로 고정합니다. 기본값은 Soft Blue입니다.

| 이름 | HEX |
| --- | --- |
| Soft Blue | `#6B94E8` |
| Fresh Mint | `#61BEA7` |
| Lilac | `#A28BE5` |
| Blush Pink | `#DF88AE` |
| Soft Coral | `#E99D83` |
| Clear Sky | `#73BADF` |

기존 루틴의 HEX 값은 자동으로 교체하지 않습니다. 편집 화면에서도 새 스와치를 누르기 전에는 원래 색상으로 저장하며, 색상/카테고리 제거를 위한 DB 마이그레이션은 없습니다. 밝은 색상 위의 체크는 네이비, 어두운 기존 색상 위의 체크는 흰색을 선택합니다. 완료 잔디와 강조선은 저장된 원색을 유지하고 큰 스트릭 숫자는 같은 계열의 읽기 쉬운 전경색을 사용합니다.

## 로고 자산

제공된 확정 시안의 세 갈래 곡선 심볼과 가는 AEHA 워드마크를 SVG 경로로 재구성했습니다. 시안의 슬로건은 앱에 포함하지 않습니다. `BrandLogo` 컴포넌트가 세 화면에서 같은 로고를 사용하며 배경에 맞춰 밝은 배경용/역상 자산을 선택합니다. 워드마크도 경로여서 외부 폰트가 필요하지 않습니다.

- `public/brand/logo-{light,dark}.svg`: 심볼 + 워드마크
- `public/brand/symbol-{light,dark}.svg`: 심볼 단독
- `public/brand/*-mono-{light,dark}.svg`: 단색/역상
- `public/brand/app-icon.svg`: 설치 아이콘 원본
- `public/favicon.svg`, `favicon-32.png`, `icon-192.png`, `icon-512.png`, `icon-maskable-512.png`, `apple-touch-icon.png`, `apple-touch-icon-v2.png`: 브라우저/PWA 자산

단일 벡터 원본은 `scripts/brand-source.mjs`입니다. 모든 PNG는 해당 SVG를 Chromium으로 렌더링하며, 일반 빌드에는 미리 생성된 파일을 사용합니다. 재생성 명령은 다음과 같습니다.

```sh
npx playwright install chromium
npm run brand:assets
# 시스템 Chromium 사용: PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run brand:assets
```

Apple PNG는 기존 `appIconSvg(true)`의 사전 라운딩·외곽선 없는 정사각형 벡터를 그대로 사용하며, 생성 시 네이비 캔버스로 불투명 출력을 명시적으로 보장합니다. HTML은 `sizes="180x180"`과 새 `apple-touch-icon-v2.png`를 참조해 URL 캐시를 구분하고, 기존 파일도 호환성과 오프라인용으로 유지합니다. 재생성한 두 Apple 파일은 기존 파일과 바이트 단위로 동일합니다. Android/마스크용 PNG와 SVG 로고도 변경되지 않았습니다.

기존 Apple PNG 검사 결과: 180×180 RGB, 전체 알파 255, 모서리 RGBA는 좌상 `(40,54,79,255)`, 우상 `(29,42,65,255)`, 좌하 `(27,39,62,255)`, 우하 `(16,28,48,255)`입니다. 가장자리 RGB 범위는 R 16~41 / G 28~55 / B 48~80이며, 외곽 4px에 투명 픽셀이나 밝은 테두리는 발견되지 않았습니다. 따라서 이미지 자체가 제보된 흰 윤곽선의 원인이라고 단정하지 않습니다. iOS의 마스킹·그림자 또는 홈 화면 아이콘 캐시 가능성은 실기기에서 확인해야 합니다. 새 URL이 웹 메타데이터에 반영되어도 이미 설치된 홈 화면 아이콘의 갱신 시점은 OS가 제어하며 보장할 수 없습니다. 기록 보존을 위해 기존 앱·사이트 데이터를 삭제하거나 재설치하는 절차를 요구하지 않습니다.

maskable 아이콘은 불투명한 배경과 중앙 80% 안전 영역을 사용합니다. 밝은 배경용·역상 로고도 서비스 워커에 포함되어 오프라인에서 테마를 바꿀 수 있습니다. manifest 이름은 AEHA, 설치 범위와 배포 경로는 기존 `/A/`를 유지합니다.

## 개발 실행

Node.js **22.12 이상**이 필요합니다. CI는 Node.js 24를 사용합니다.

```sh
npm ci
npm run dev
```

기본 개발 경로는 `http://localhost:5173/A/`입니다.

```sh
npm test               # Vitest: 날짜·일정·스트릭·저장 계층
npm run test:watch     # 테스트 감시
npm run typecheck      # TypeScript 검사
npm run build          # TypeScript 검사 후 dist/ 프로덕션 빌드
npm run preview        # 빌드 결과를 로컬에서 확인
```

PWA 서비스 워커와 오프라인 동작은 개발 서버 대신 프로덕션 빌드의 preview에서 확인합니다. 기본 preview 경로는 `http://localhost:4173/A/`입니다.

### 실제 브라우저 테스트

```sh
npx playwright install chromium
npm run build
npm run test:e2e
```

Linux 시스템 라이브러리도 필요하다면 `npx playwright install --with-deps chromium`을 사용합니다. 설치된 Chromium을 사용할 때는 다음과 같이 실행할 수 있습니다.

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e
```

Playwright는 모바일 화면 크기의 Chromium에서 빌드 결과를 실행합니다. 설정된 테스트 경로는 `/A/`이므로 다른 base로 빌드했다면 `VITE_BASE_PATH=/A/ npm run build` 후 실행하세요. 브라우저 자동화는 실제 Android·iPhone의 홈 화면 설치 검증을 대체하지 않습니다.

### 구현 시 검증 결과

- `npm test`: 단위·저장 계층·마이그레이션·체크 색상 대비·반복 일정·오늘 완료 판정 테스트 **105개 통과**.
- 날짜·일정·스트릭 테스트 **43개**는 UTC, Asia/Seoul, America/New_York 각각에서 통과.
- `npm run build`: TypeScript 검사와 프로덕션/PWA 빌드 통과. SVG 로고·favicon·설치 아이콘을 생성하고 빌드 산출물에 포함한 것을 확인했습니다. Chromium에서는 세 화면의 테마별 로고 표시, 오프라인 라이트/다크 로고 로딩, 아이콘 PNG 크기를 검증했습니다.
- Playwright Chromium: **55개 통과**. 기존 v2 데이터를 가진 상태에서 마무리·취소·저장 실패·삭제 분리·진행률 제외·마무리 당일 체크/취소 보존, 수개월 후 및 오프라인 재실행의 잔디 고정, 320px 한/영·라이트/다크 완료 기록을 검증했습니다. 신규 사용자 다크 초기 프레임(힌트 저장소 불가 포함), 기존 라이트/다크·언어·기록 보존, 잘못된 힌트 보정과 Apple PNG의 전체 알파·외곽/모서리 픽셀·오프라인 읽기도 검증했습니다. 수동 순서의 스트릭 동기화·생성 순서 폴백, 전체 완료·취소·재완료·재실행·0개 대상·저장 실패·모션 줄이기를 검증했습니다. standalone 웹 시작·테마 캐시·오프라인 재실행, 한/영 액션 메뉴와 확인 전 삭제 방지, 삭제 후 원본 기록 보존, 쉼표 일정 및 터치/마우스/키보드 요일 포커스를 검증했습니다. 높이가 다른 메모 카드의 반복 완료·취소 이동도 검증했습니다. 완료·취소 양방향 300ms 실제 이동과 카드 DOM/가시성 유지, 모션 줄이기, 저장 지연 시 즉시 체크, 저장 실패 시 원복, 다른 탭에 의한 업그레이드 차단·연결 해제 후 복구, 버전 변경 시 안전한 연결 종료, 초기 읽기 지연 안내를 검증했습니다. 생성·수정·삭제, 체크·취소, 새로고침 보존, 일정 변경, 자정 직후 체크, 언어 선택 목록·테마, 기존 시스템 테마의 일회성 전환과 데이터 보존, 두 테마의 루틴별 색상·이전 잔디 재표시, AEHA 이름·매니페스트, 320px/375px/390px에서 완료·미완료·비대상 루틴이 섞인 홈과 버튼 겹침 방지, 한국어/영어 월 레이블·셀 정렬·가로 스크롤·마지막 카드의 내비게이션 여백, `/A/` 아이콘·서비스 워커, 오프라인 새로고침·기록을 검증. 구버전 v1 IndexedDB의 실제 업그레이드·기록 보존, 마우스·터치·키보드 정렬, 취소와 체크/편집 분리도 검증합니다. 테스트 데이터는 매번 격리된 브라우저 컨텍스트에서만 생성합니다.
- 실제 Android/iPhone 홈 화면 설치와 기기에서의 업데이트 재현은 아직 검증하지 않았습니다. GitHub Actions의 테스트·빌드·Chromium E2E 성공 후 Pages에 배포합니다.

## 기록과 날짜 규칙

### 수동 순서와 안전한 업그레이드

- DB 이름 `eha-habit`과 기존 세 테이블·기본 키·수행 기록의 고유 인덱스를 유지합니다. Dexie 버전 1 선언도 그대로 둡니다.
- 버전 2는 `routines.sortOrder`와 인덱스만 추가합니다. 업그레이드 트랜잭션 안에서 기존 생성 시각·ID 표시 순서를 정렬값으로 부여하며, DB나 테이블을 삭제·초기화하지 않습니다.
- 기존 이름·메모·색상·일정 이력·시각·삭제 상태와 모든 완료/취소 레코드·설정을 보존합니다. 마이그레이션이 실패하면 트랜잭션이 롤백되며 자동으로 데이터를 지우지 않습니다.
- 수동 순서와 완료에 따른 표시 순서는 분리되어 있습니다. 체크·체크 취소는 `sortOrder`를 수정하지 않습니다. 비대상 루틴은 항상 마지막 그룹에 표시합니다. 스트릭도 같은 `compareManualOrder`로 기본 수동 순서를 표시하며, 홈의 완료 그룹 이동은 스트릭에 반영하지 않습니다. 정렬값이 없는 기존 데이터는 생성 시각·ID 순서를 사용합니다. 이를 위해 새 필드나 마이그레이션을 추가하지 않습니다.
- 드래그는 같은 상태 그룹의 기존 수동 위치끼리 바꿉니다. 다른 그룹의 위치와 수행 기록을 덮어쓰지 않으며, 새 루틴은 수동 순서의 마지막에 추가됩니다.
- 모바일은 왼쪽 핸들에서 드래그합니다. 본문에서는 스크롤할 수 있고 체크·편집 버튼은 독립적으로 동작합니다. 키보드는 핸들에 초점을 두고 Space → 위/아래 → Space로 저장하며 Escape로 취소합니다.
- 체크 상태는 저장을 기다리지 않고 즉시 표시합니다. 완료·취소에 따른 카드 이동은 기존 sortable의 레이아웃 애니메이션으로 300ms 동안 함께 움직이며, 다음 취소에서도 이전 위치를 사용할 수 있도록 재정렬 후 위치 측정값을 갱신합니다. 저장 실패 시 체크와 표시 순서를 되돌리고 오류를 안내합니다. `prefers-reduced-motion: reduce`에서는 이동 모션을 제거합니다.
- 구버전 Dexie DB와 실제 Chromium의 네이티브 v1 IndexedDB에 데이터가 있는 상태에서 업그레이드하는 테스트를 실행합니다. 루틴·완료·취소·삭제 기록·설정 보존과 재실행 후 순서 유지, 실패 시 롤백을 검증합니다. 테스트 데이터는 별도 DB 또는 격리된 브라우저 컨텍스트에서만 만듭니다.

### 루틴 마무리와 기록 보관

일일 체크와 장기적인 마무리는 별개입니다. 점 세 개 메뉴의 **루틴 마무리**에서 확인하면 기존 루틴에 선택적 `finishedAt`(ISO 시각), `finishedDate`(당시의 로컬 날짜)와 `updatedAt`만 저장합니다. `deletedAt`은 설정하지 않습니다. 필드가 없는 기존 루틴은 진행 중으로 취급하며 DB 이름 `eha-habit`, Dexie 버전 2, 테이블·인덱스·키는 그대로입니다. 인덱스가 없는 선택적 속성을 확장하므로 새 스키마 업그레이드나 초기화가 필요하지 않습니다.

마무리 당일은 **포함**합니다. 기존 체크가 true면 유효한 수행일로 집계하고, 취소(false) 또는 미기록이면 그대로 둡니다. 체크를 자동 생성하지 않으며, 완료·취소 행의 ID·시각과 모든 과거/미래 일정 이력을 변경하지 않습니다. 총 완료 일수와 최장 연속은 시작일부터 마무리일까지 기존 일정·스트릭 규칙으로 계산합니다. 비대상일은 연속 기록을 끊지 않습니다. 잔디의 26주 창과 마지막 날짜 표시는 저장한 로컬 마무리일을 기준으로 고정되어 이후 날짜·시간대가 달라져도 이동하지 않습니다. 표시 범위보다 오래된 기록도 DB에 남습니다.

진행 중 화면은 기존 수동 순서, 완료 기록은 최근 마무리 시각 순서(동률이면 수동 순서)를 사용합니다. 마무리한 루틴은 홈·오늘 진행률·드래그 대상에서 제외하며, 추가 체크/취소·수정은 저장 계층에서도 거절합니다. 반복 마무리 요청은 최초 마무리 날짜를 바꾸지 않습니다. 삭제는 별도의 soft-delete이며 보관으로 취급하지 않습니다. 이번 버전의 완료 기록은 읽기 전용이며 재개 기능은 제공하지 않습니다. 데이터는 향후 재개가 가능하도록 비파괴적으로 보존합니다. 마무리만으로 전체 완료 강조 이벤트를 새로 실행하지 않습니다.

### 오늘 전체 완료 피드백

오늘 수행 대상이 1개 이상이고 모두 완료된 경우 진행 바는 Midnight Sapphire 완료 색상과 100% 폭을 유지하고, 작은 체크와 `오늘도 완료!` / `All done today!`를 표시합니다. 마지막 체크의 IndexedDB 저장·재조회가 성공하면 진행 바는 550ms, 색상·카드 배경·테두리는 500ms, 문구·체크는 300ms 동안 겹쳐 전환됩니다. easing은 `cubic-bezier(0.22, 1, 0.36, 1)`이며, 완료 색상은 라이트에서 진행 바 `#405C86`·문구/체크 `#344F78`·배경 `#F0F3F8`·테두리 `#C5D0E0`, 다크에서 진행 바 `#879FCB`·문구/체크 `#B4C6E8`·배경 `#202D42`·테두리 `#485E80`를 사용합니다. 은은한 완료 배경·테두리는 전환 뒤에도 유지하며, 플래시·펄스·배경 복귀 효과는 없습니다. 완료를 취소하면 일반 상태로 부드럽게 돌아오고 재완료하면 같은 전환을 재생합니다. 이미 완료된 앱을 열거나 홈으로 복귀할 때는 최종 상태만 표시합니다. 대상이 0개이거나 저장에 실패한 경우 성공 상태를 만들지 않으며, 모션 줄이기에서는 모든 전환 없이 즉시 상태를 표시합니다. 연출 상태는 메모리에만 두며 DB 구조와 기록은 변경하지 않습니다. Chromium에서는 실제 프레임의 진행 바 이동·배경색 변화가 양쪽 상태 사이에서만 진행되고 원래 색으로 되돌아가지 않는지도 확인합니다.

### 업데이트 중 연결 대기와 복구

- 다른 탭의 연결이 버전 변경 요청에도 열린 채로 남으면 IndexedDB 업그레이드 요청은 끝나지 않고 `blocked` 상태로 대기할 수 있습니다. 이 경로를 실제 Chromium의 별도 탭으로 재현했습니다. 당시 Android 현상의 정확한 원인은 기기 로그가 없어 단정하지 않습니다.
- 새 코드는 `blocked`를 즉시 안내하고, DB 열기나 초기 읽기가 8초 이상 걸리는 경우에도 로딩 문구 대신 다른 AEHA 창 종료·다시 시도·새로고침 방법을 표시합니다. 대기 중 재시도는 같은 요청을 공유하며 업그레이드 요청을 중복 생성하지 않습니다. 차단 연결이 닫히면 기존 요청으로 자동 복구합니다.
- 버전 변경 요청을 받은 기존 AEHA 연결은 진행 중인 트랜잭션이 끝나도록 안전하게 닫고, 오래된 코드의 자동 재연결을 막습니다. 해당 창에는 새로고침 안내를 표시합니다.
- 이 처리는 DB 이름 `eha-habit`, Dexie v2 스키마, 루틴·완료/취소 기록·설정을 유지하며 DB 삭제나 초기화를 호출하지 않습니다. 이번 변경에서는 스키마 버전을 올리지 않습니다.
- 실제 Android에서는 Chrome 탭과 설치된 PWA를 함께 열어 둔 상태의 업데이트, 안내 표시, 다른 창 종료 후 기록 복구를 추가 확인해야 합니다. 사이트 데이터 삭제를 복구 방법으로 사용하지 마세요.

### 날짜와 스트릭

- 날짜 키는 사용자의 **로컬 달력 날짜**인 `YYYY-MM-DD`입니다. UTC 타임스탬프와 별도로 `createdDate`를 저장하여 루틴 생성일이 시간대 때문에 밀리지 않도록 합니다.
- 연속 기록은 수행 대상일의 완료 횟수입니다. 비대상일과 생성 이전 날짜는 실패로 계산하지 않습니다.
- 오늘 아직 체크하지 않았어도 이전 스트릭을 유지합니다. 완료하면 즉시 포함하며, 지나간 수행일을 놓쳤다면 끊깁니다.
- 기존 루틴의 반복 요일 변경은 **내일부터 적용**됩니다. 이름·메모·카테고리·색상은 바로 적용됩니다. 일정 이력은 보존하며 같은 날 여러 번 수정하면 내일부터 적용할 일정만 갱신합니다. 오늘의 완료 기록과 과거 날짜의 의미는 유지됩니다.
- `[routineId+date]` 고유 인덱스와 트랜잭션으로 한 루틴·날짜의 중복 기록을 방지합니다. 완료 취소는 같은 레코드의 `completed: false`로 남깁니다. 삭제는 `deletedAt`을 기록하고 목록에서 숨깁니다.
- 스트릭 숫자를 별도 저장하지 않고 일정 이력과 수행 기록으로 계산합니다.

모든 데이터는 현재 브라우저의 IndexedDB에 저장됩니다. 새로고침이나 앱 종료 후에도 유지되지만, 사이트 데이터 삭제·브라우저 저장 공간 정리·기기 변경 시 복구할 수 없습니다. 계정 동기화와 백업/내보내기 기능은 제공하지 않습니다. 같은 기기라도 브라우저나 사이트 주소가 달라지면 저장 공간이 다를 수 있습니다.

## 시작 연출과 시스템 영역

설치형 앱의 웹 콘텐츠가 준비되는 동안 기존 심볼+워드마크 SVG를 즉시 표시합니다. 캐시된 빠른 실행에서도 로고가 실제 첫 프레임에 그려진 다음 약 180ms로 홈에 크로스페이드합니다. React 홈 렌더링·DB 읽기·입력을 애니메이션 종료까지 기다리게 하지 않으며 별도 최소 대기 타이머는 없습니다. 이전의 100ms 생략 조건과 로고 표시 지연은 제거했습니다. `prefers-reduced-motion`에서는 시작 레이어를 표시하지 않으며 오류·차단·지연 안내가 나오면 즉시 제거합니다. 기존 내부 데이터 로딩 문구와는 독립적입니다.

초기 HTML·React 초기 테마·IndexedDB 기본 설정은 모두 다크로 시작하며, manifest의 딥 네이비 배경과 맞춥니다. 명시적인 라이트 힌트가 있으면 첫 렌더링 전에 라이트를 적용합니다. `aeha-theme-hint`는 마지막으로 성공적으로 읽은 테마의 표시용 캐시입니다. IndexedDB 설정이 여전히 원본이며 캐시가 잘못되었거나 저장할 수 없어도 루틴 기록에는 영향을 주지 않습니다. 테마를 읽으면 캐시와 실제 설정을 맞춥니다. PWA 설치 ID, 시작 주소 `/A/`, scope와 기존 아이콘 파일은 그대로입니다. Apple 아이콘 참조에만 캐시 구분용 v2 파일을 사용합니다.

manifest의 기본 `background_color`와 `theme_color`는 AEHA 다크 배경(`#121A27`)으로 맞춥니다. 웹이 표시되면 `meta[name="theme-color"]`는 하단 탭 배경과 같은 라이트 `#FFFFFF`, 다크 `#161F2D`로 적용합니다. 기존 safe-area 패딩은 유지하고 시스템 제스처 위에 별도 가림막을 만들지 않습니다.

Android가 manifest로 생성하는 네이티브 스플래시와 시스템 제스처 영역은 OS·Chrome 버전이 제어합니다. 웹 시작 레이어와는 별개이며 웹 CSS로 완전히 바꿀 수 없습니다. 정적인 OS 스플래시는 저장된 라이트/다크 테마를 즉시 반영하지 못할 수 있습니다. 웹 연출은 새 service worker의 HTML/JS/CSS 캐시가 활성화된 뒤 새 문서를 열면 재설치 없이 반영됩니다. 이미 열린 문서는 이전 JS를 계속 실행할 수 있으므로 온라인에서 앱 창을 닫고 다시 열거나 새로고침해 확인합니다. Android OS 시작 화면은 별도의 Chrome/WebAPK 메타데이터 캐시를 사용하므로 service worker 갱신만으로 즉시 바뀐다고 보장하지 않습니다. 기존 설치본의 자동 메타데이터 갱신 시점은 기기·Chrome 버전에 따라 달라지며, 재설치를 필수 절차로 요구하지 않습니다. 사이트 데이터나 앱을 삭제하는 방식으로 확인하지 마세요. Chromium 테스트는 웹 standalone 상태를 에뮬레이션하며 실제 Android 시작 화면·시스템 영역 확인을 대신하지 않습니다. 업데이트를 위해 앱 삭제나 재설치는 필요하지 않습니다.

홈의 반복 일정은 해당 날짜에 실제 유효한 이력을 사용해 월요일→일요일 순서로 표시합니다(`화,금,일` / `Tue,Fri,Sun`). 쉬는 날에는 `오늘은 쉬는 날 (화,금,일)`을 사용하며 360px 이하에서는 요일만 간결하게 표시하되 전체 상태는 접근성 이름과 title에 유지합니다. 요일 선택 버튼도 월~일 순서이며, 내부 요일 번호(일요일=0)와 저장된 이력은 변경하지 않습니다. 요일 선택의 채워진 배경과 키보드용 안쪽 점선 포커스는 구분하고, 터치·마우스 조작에는 추가 포커스 외곽선을 표시하지 않습니다.

## PWA 설치와 오프라인

HTTPS로 배포된 앱에서 다음과 같이 설치할 수 있습니다.

- **Android Chrome**: 브라우저 메뉴의 앱 설치 또는 홈 화면에 추가를 사용합니다.
- **iPhone Safari**: 공유 메뉴 → 홈 화면에 추가를 사용합니다.

앱 자체의 설치 안내 팝업은 없습니다. 매니페스트, 일반/마스크용 아이콘, Apple 터치 아이콘, standalone 모드와 모바일 safe-area를 제공합니다. 처음 온라인으로 방문해 서비스 워커가 필요한 리소스를 캐시한 뒤에는 오프라인에서도 실행·기록할 수 있습니다. 처음 방문하기 전에는 오프라인 실행할 수 없습니다.

## GitHub Pages 배포

`.github/workflows/deploy.yml`은 `main` 변경 시 다음 순서로 실행됩니다.

1. `npm ci`
2. `npm test`
3. `npm run build` — TypeScript 검사 포함
4. 설치된 Chromium 계열 브라우저 사용(없으면 설치) 후 `npm run test:e2e` — 이동 모션·터치 정렬·업그레이드 차단과 복구 포함
5. `dist/` 아티팩트 업로드 및 GitHub Pages 배포

Pull Request에서는 테스트와 빌드만 수행하며 배포하지 않습니다. Actions 화면에서 수동 실행도 가능합니다. 배포 job에는 `pages: write`와 `id-token: write`, 빌드에는 `contents: read` 권한이 선언되어 있습니다.

공개하려면 저장소 관리자가 다음을 진행해야 합니다.

1. GitHub 저장소의 **Settings → Pages → Build and deployment → Source**를 **GitHub Actions**로 설정합니다.
2. **Settings → Actions → General**에서 Actions 및 워크플로가 사용하는 공식 GitHub Actions의 실행을 허용합니다. 조직 정책이 권한을 제한하면 관리자의 허용이 필요합니다.
3. 이 소스코드를 커밋해 `main`에 push하거나 Pull Request를 병합합니다. `github-pages` 환경에 승인 규칙이 있다면 배포를 승인합니다.
4. **Actions**에서 워크플로 성공과 Pages에 표시되는 실제 배포 URL을 확인합니다.

현재 저장소 `esae-dev/A`의 **예상 배포 주소**는 **https://esae-dev.github.io/A/** 입니다. 워크플로 파일을 작성한 것만으로 실제 배포가 완료되지는 않습니다.

Vite의 기본 base는 `/A/`입니다. Actions에서는 `GITHUB_REPOSITORY`의 저장소 이름을 읽어 `/<저장소명>/`을 적용하며 `*.github.io` 저장소는 `/`을 사용합니다. 매니페스트의 `id`, `start_url`, `scope`와 서비스 워커의 탐색 경로도 같은 base를 사용합니다.

커스텀 도메인이나 다른 경로로 배포할 경우 앞뒤 `/`를 포함한 경로로 빌드하세요.

```sh
VITE_BASE_PATH=/ npm run build
# 또는 VITE_BASE_PATH=/example/ npm run build
```

지속적으로 변경하려면 배포 워크플로의 build 단계에도 `VITE_BASE_PATH` 환경 변수를 지정해야 합니다. 이 설정만으로 GitHub의 커스텀 도메인/DNS가 구성되지는 않습니다.

## 프로젝트 구조

```text
src/
  App.tsx               세 화면과 사용자 동작
  components/           루틴 편집, 스트릭 카드, 선형 아이콘
  domain/               데이터 타입, 로컬 날짜, 일정, 순수 스트릭 계산과 테스트
  data/                 버전 관리 Dexie 스키마, 저장소 API와 테스트
  i18n.ts               한국어·영어 UI 리소스
  styles.css            반응형 레이아웃, 테마, safe-area
public/                 로컬 앱 아이콘
e2e/                    Playwright 브라우저 테스트
.github/workflows/      테스트·빌드·Pages 배포
```

화면은 저장소 API를 사용하고 IndexedDB에 직접 접근하지 않습니다. UUID, 수정 시각, 삭제/완료 취소 상태와 버전 관리 스키마는 데이터 확장을 위한 기반이며 현재 서버나 동기화 엔진은 없습니다.
